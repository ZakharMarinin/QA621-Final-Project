# ТЗ №1: «Магазин» — корзина и заказы в терминале

## 1. Суть проекта

Консольное приложение небольшого интернет-магазина: каталог товаров,
корзина, промокоды, оформление и отмена заказов, учёт остатков на складе.
Товары разных типов по-разному считают стоимость и по-разному ограничивают
количество, промокоды разных типов по-разному считают скидку. Все данные
хранятся между запусками в JSON-файлах.

Вторая половина задания — **автотесты на pytest**. Магазин — это система,
которую вы не только пишете, но и тестируете: к сдаче прикладывается набор
тестов, который доказывает, что корзина, скидки и склад работают правильно
(см. раздел 8). Без тестов проект не принимается.

Это НЕ веб-сервер и не настоящая оплата — «оформить заказ» значит списать
товары со склада и записать заказ в JSON.

## 2. Формат работы

Приложение запускается из терминала с аргументами командной строки
(`sys.argv` или `argparse`) либо как интерактивное меню в цикле — на выбор
студента, но выбранный формат должен быть описан в README.

Примеры команд (командный стиль):

```
python main.py catalog
python main.py catalog --category coffee
python main.py search кофе
python main.py show P003
python main.py cart add P003 2
python main.py cart add P010 0.35
python main.py cart set P003 1
python main.py cart remove P003
python main.py cart show
python main.py promo SALE10
python main.py checkout
python main.py orders
python main.py order 1
python main.py cancel 1
python main.py restock P003 10
python main.py export-orders reports/orders.csv
```

Конкретные названия команд и флагов студент может адаптировать, но набор
сценариев (п. 3) должен быть полностью покрыт.

## 3. Функциональные требования

1. **Каталог** — список товаров: артикул, название, категория, цена,
   остаток на складе. Фильтр по категории.
2. **Поиск** — по подстроке в названии, без учёта регистра.
3. **Карточка товара** — подробная информация, включая тип товара и его
   особенности (например, «цена за кг» или «цифровой, доставка на email»).
4. **Корзина** — добавить товар с количеством, изменить количество, убрать
   товар, показать корзину: позиции, количество, сумма по каждой строке,
   сумма без скидки, скидка, итог к оплате. Повторное добавление того же
   товара увеличивает количество, а не создаёт вторую строку.
5. **Промокод** — к корзине применяется один промокод (новый заменяет
   старый). Промокоды разных типов считают скидку по-разному (п. 4).
   Неизвестный промокод или промокод, условия которого не выполнены
   (например, сумма меньше порога), — понятное сообщение.
6. **Оформление заказа** — проверка остатков по всем позициям, списание
   остатков со склада, создание заказа (номер, позиции, сумма, скидка,
   итог, статус `new`), очистка корзины. Если хотя бы одной позиции не
   хватает — заказ не создаётся и склад не меняется вообще (никаких
   «частично списали»).
7. **История заказов** — список заказов (номер, количество позиций, итог,
   статус) и просмотр конкретного заказа.
8. **Отмена заказа** — статус меняется на `cancelled`, остатки
   возвращаются на склад. Отменить уже отменённый заказ нельзя.
9. **Приход товара** — увеличение остатка товара (команда «администратора»,
   без авторизации).
10. **Экспорт** — выгрузка всех заказов в CSV (одна строка — один заказ:
    номер, статус, количество позиций, сумма, скидка, итог).
11. **Журнал действий** — значимые действия (добавление в корзину,
    применение промокода, оформление, отмена) пишутся в текстовый лог
    `data/shop.log` **с помощью декоратора** (см. п. 5).
12. **Обработка ошибок** — несуществующий артикул, количество ≤ 0 или не
    числом, нехватка остатка, неверный промокод, оформление пустой корзины,
    отсутствующий или повреждённый JSON — понятное сообщение, а не
    traceback.

## 4. Требования к товарам и скидкам

### 4.1. Типы товаров (минимум 3)

Каждый тип должен реально отличаться поведением, а не только полем `type`:

- **Штучный** (`piece`) — количество только целое, не больше остатка.
- **Весовой** (`weight`) — цена указана за 1 кг, количество — дробное
  число килограммов (например, `0.35`), есть минимальный вес (например,
  0.1 кг); сумма строки округляется до копеек.
- **Цифровой** (`digital`) — склада нет (остаток не проверяется и не
  списывается), в корзине может быть максимум 1 штука.

Можно предложить свои типы (например, «товар 18+», «товар под заказ»), но
не меньше трёх с различающимся поведением.

### 4.2. Типы промокодов (минимум 3)

- **Процентная скидка** — например, `SALE10`: −10% от суммы корзины.
- **Фиксированная скидка от порога** — например, `MINUS500`: −500 ₽, если
  сумма корзины не меньше 3000 ₽. Скидка не может сделать итог
  отрицательным.
- **«3 по цене 2»** или **скидка на категорию** — например, `COFFEE3`:
  каждый третий штучный товар категории `coffee` бесплатно; или `TEA15`:
  −15% только на товары категории `tea`.

### 4.3. Минимум данных

- Не менее **10 товаров** в каталоге, не менее **3 категорий**.
- Все три типа товаров представлены в каталоге.
- Не менее **3 промокодов** разных типов в конфиге.

## 5. Требования к коду

### 5.1. ООП — обязательны все 4 принципа

Требование к ООП — центральная часть оценки. Ниже описано, **где именно**
каждый принцип должен быть виден в коде (копировать структуру дословно не
обязательно, но принципы должны присутствовать по существу):

- **Абстракция.** Базовый класс `Product` — абстрактный класс через
  `abc.ABC` с абстрактными методами, например `line_price(qty)` (стоимость
  строки) и `check_qty(qty)` (проверка допустимого количества). Аналогично
  `Discount` — абстрактный класс с методом `apply(cart)`, возвращающим
  размер скидки. Создать `Product()` или `Discount()` напрямую нельзя.
- **Инкапсуляция.** Цена и остаток хранятся в защищённых атрибутах
  (`_price`, `_stock`) и доступны через `@property`. Сеттеры валидируют
  значения: цена > 0, остаток ≥ 0. Списать со склада больше, чем есть,
  нельзя — метод товара кидает собственное исключение.
- **Наследование.** `PieceProduct`, `WeightProduct`, `DigitalProduct`
  наследуются от `Product`, используют `super().__init__()` и
  переопределяют поведение. Типы промокодов — наследники `Discount`.
- **Полиморфизм.** Корзина считает сумму, вызывая `product.line_price(qty)`
  для каждой строки, а скидку — `discount.apply(cart)`, **не проверяя тип**
  через `if isinstance(...)` или `if product.type == "weight"`. Разное
  поведение обеспечивают переопределённые методы, а не ветвление в
  вызывающем коде.

### 5.2. Остальные обязательные элементы

- **Композиция.** `Cart` хранит строки корзины и (опционально) промокод;
  `Shop`/`ShopService` владеет каталогом, корзиной и заказами.
- **Дандер-методы — минимум 2 осмысленных.** Например, у `Cart`:
  `__len__` (количество позиций), `__iter__` (перебор строк),
  `__contains__` (`"P003" in cart`), `__bool__` (пустая ли корзина);
  у `Order` — `__str__` для красивого вывода.
- **dataclasses — минимум 1.** Например, `CartItem(product_id, qty)` и
  `Order(id, items, subtotal, discount, total, status)`;
  `asdict()` — для сохранения в JSON.
- **Собственные исключения** с общим родителем: `ShopError` →
  `ProductNotFoundError`, `OutOfStockError`, `InvalidQuantityError`,
  `InvalidPromoError`, `EmptyCartError`, `OrderError` (названия — на
  усмотрение студента). CLI ловит `ShopError` в одном месте и печатает
  сообщение.
- **Декоратор — минимум 1, по делу.** Например, `@log_action`, который
  записывает в `data/shop.log` имя действия, аргументы и результат
  (успех/ошибка) — применяется к методам сервиса.
- **Фабрика из JSON.** Промокоды из `promos.json` превращаются в объекты
  нужного класса через словарь `{"percent": PercentDiscount, ...}` — как
  стенд из JSON-конфига на практикуме по ООП (занятие 27-28). Неизвестный
  тип в конфиге — понятная ошибка с указанием, какой промокод сломан.

## 6. Хранение данных (JSON как база данных)

Три файла в `data/` (пути можно изменить, но зафиксировать в README).

### 6.1. `data/catalog.json` — товары и остатки (чтение и запись)

```json
{
  "products": [
    {"id": "P001", "type": "piece", "name": "Кружка QA", "category": "merch", "price": 590, "stock": 12},
    {"id": "P003", "type": "piece", "name": "Кофе в зёрнах 250 г", "category": "coffee", "price": 790, "stock": 8},
    {"id": "P010", "type": "weight", "name": "Чай улун (на развес)", "category": "tea", "price_per_kg": 2400, "min_kg": 0.1, "stock_kg": 3.5},
    {"id": "P020", "type": "digital", "name": "Курс «Pytest за выходные»", "category": "courses", "price": 1990}
  ]
}
```

### 6.2. `data/promos.json` — промокоды (только чтение)

```json
{
  "promos": [
    {"code": "SALE10", "type": "percent", "percent": 10},
    {"code": "MINUS500", "type": "fixed", "amount": 500, "min_total": 3000},
    {"code": "COFFEE3", "type": "three_for_two", "category": "coffee"},
    {"code": "TEA15", "type": "category_percent", "category": "tea", "percent": 15}
  ]
}
```

### 6.3. `data/orders.json` — корзина и заказы (чтение и запись)

```json
{
  "cart": {
    "items": [{"product_id": "P003", "qty": 2}, {"product_id": "P010", "qty": 0.35}],
    "promo": "SALE10"
  },
  "orders": [
    {
      "id": 1,
      "items": [{"product_id": "P001", "qty": 1, "price": 590, "line_total": 590}],
      "subtotal": 590,
      "discount": 0,
      "total": 590,
      "promo": null,
      "status": "new"
    }
  ],
  "next_order_id": 2
}
```

Обратите внимание: в заказе хранится **цена на момент покупки**
(`price`, `line_total`) — если цена товара в каталоге потом изменится,
старый заказ не должен «пересчитаться».

Требования к работе с JSON:

- Чтение/запись через модуль `json` в отдельном классе/модуле
  (`Repository`/`Storage`), а не разбросанные по коду
  `open()`/`json.load()`.
- Путь к файлам передаётся в `Repository` параметром (а не зашит внутри
  методов) — иначе его не получится протестировать на временных файлах
  (см. раздел 8).
- Сохранение — после каждого изменяющего действия.
- Отсутствует `orders.json` — создаётся пустой автоматически.
  Отсутствует или повреждён `catalog.json`/`promos.json` — понятное
  сообщение, а не traceback.
- `ensure_ascii=False` и `indent` — файлы должны читаться человеком.

## 8. Автотесты (pytest) — обязательная часть

- Тесты лежат в `tests/`, общие фикстуры — в `tests/conftest.py`, в корне
  проекта — `pytest.ini` с `pythonpath = .` (как на занятии 29-30).
  Команда `pytest` из папки проекта запускает все тесты без ошибок
  импорта.
- **Не меньше 15 тестов**, все зелёные на момент сдачи.
- **Не меньше 3 фикстур**, например: каталог из нескольких товаров разных
  типов, пустая корзина, корзина с товарами, `Repository` на временных
  файлах.
- **Хотя бы одна фикстура использует `tmp_path`** (или `yield` с уборкой):
  тесты **не имеют права** читать и менять настоящие `data/*.json`.
- **`pytest.raises`** — на каждое собственное исключение хотя бы один тест.
- **Хотя бы один тест-класс** (`class TestCart:`), группирующий тесты одной
  сущности.
- Что обязательно покрыть:
  - стоимость строки для каждого типа товара (в том числе округление у
    весового);
  - ограничения количества для каждого типа (дробное у штучного, 2 штуки
    цифрового, вес меньше минимального);
  - каждый тип промокода, включая «порог не выполнен» и «скидка не больше
    суммы»;
  - оформление заказа уменьшает остатки, а при нехватке хотя бы одной
    позиции — не меняет склад вообще;
  - отмена заказа возвращает остатки, повторная отмена — ошибка;
  - `Repository`: сохранили → загрузили → данные совпали; повреждённый
    JSON → собственное исключение.
- Имена тестов говорят, что проверяется:
  `test_weight_product_rounds_line_price_to_kopecks`, а не `test_1`.

`@pytest.mark.parametrize`, маркеры и HTML-отчёты не требуются (это темы
следующих занятий) — но если разберётесь сами, это плюс (п. 12).
