# ТЗ №2: «Валидатор» — проверка тестовых данных по правилам

## 1. Суть проекта

Консольный QA-инструмент: берёт файл с тестовыми данными (CSV или JSON —
пользователи, заказы, товары) и проверяет каждую запись по набору правил,
описанному в отдельном JSON-конфиге: обязательные поля, типы, диапазоны,
длина строк, формат email, допустимые значения, уникальность. По итогам
печатает сводку и сохраняет отчёт в одном из четырёх форматов.

Такие инструменты реально используют в тестировании: прежде чем заливать
тестовые данные на стенд или гонять на них автотесты, их проверяют — иначе
тест падает не из-за бага в продукте, а из-за кривого `age = "abc"` в
фикстуре.

Ключевая архитектурная идея: **правила — это данные, а не код**. Чтобы
проверить новый файл, пользователь пишет новый `rules.json`, а не правит
Python. Код знает только, какие типы правил существуют и как их применить.

Вторая половина задания — **автотесты на pytest** на сам валидатор: каждое
правило, загрузчики, конфиг, отчёты (см. раздел 8). Без тестов проект не
принимается. Да, это тесты для инструмента тестирования — так и задумано.

## 2. Формат работы

Утилита запускается из терминала с аргументами командной строки
(`sys.argv` или `argparse`). Интерактивное меню здесь не подходит — такие
инструменты запускают из скриптов и CI.

```
python main.py check data/users.csv --rules rules/users.json
python main.py check data/users.csv --rules rules/users.json --report md
python main.py check data/orders.json --rules rules/orders.json --report csv
python main.py rules
```

Пример вывода в консоль (для файла из 6 записей):

```
$ python main.py check data/users.csv --rules rules/users.json --report md
Проверка data/users.csv по правилам rules/users.json

Запись 2  email   email     'boris@example' — некорректный email
Запись 3  name    required  обязательное поле пустое
Запись 3  age     range     17 вне диапазона 18..120
Запись 4  id      unique    '2' уже встречался в записи 2
Запись 4  role    one_of    'manager' нет в списке: guest, tester, admin
Запись 5  age     type      'abc' — ожидали int
Запись 6  email   unique    'anna@example.com' уже встречался в записи 1

Итого: записей 6, без ошибок 1, с ошибками 5, нарушений 7
Отчёт сохранён: reports/users_report.md
```

Точный формат вывода — на усмотрение студента; набор информации (номер
записи, поле, правило, сообщение, сводка) — обязателен.

## 3. Функциональные требования

1. **Загрузка данных** — CSV (с заголовком) или JSON (список объектов);
   формат определяется по расширению файла. Результат загрузки — список
   словарей, дальше валидатор работает одинаково независимо от формата.
2. **Загрузка правил** — JSON-конфиг (п. 6.2) превращается в объекты
   правил. Конфиг проверяется **до** прогона данных: неизвестное правило,
   не хватает параметра, `min > max` — понятная ошибка с указанием поля и
   правила, где проблема.
3. **Прогон** — каждая запись проверяется всеми правилами своих полей.
   Нарушение — это объект с номером записи, полем, именем правила,
   значением и сообщением. Одна запись может дать несколько нарушений.
4. **Пустые значения.** Если значение пустое (`""`, `null` или поля нет
   вовсе) — его проверяет только `required`; остальные правила пустые
   значения пропускают. Иначе одно пустое поле даст пять одинаковых
   ошибок.
5. **Сводка** — всего записей, без ошибок, с ошибками, общее количество
   нарушений, количество нарушений по каждому правилу и по каждому полю.
6. **Отчёты** — `console` (по умолчанию, только вывод на экран), `csv`
   (одна строка — одно нарушение), `json` (сводка + список нарушений), `md`
   (Markdown-таблица нарушений + сводка). Файловые отчёты сохраняются в
   `reports/`, папка создаётся автоматически.
7. **Список правил** — команда `rules` печатает доступные правила и их
   параметры (берётся из того же реестра, что использует фабрика, а не
   из отдельного захардкоженного текста).
8. **Код выхода** — `0`: нарушений нет; `1`: есть нарушения; `2`: ошибка
   запуска (нет файла, битый файл, ошибка в конфиге, неверные аргументы).
   Так утилиту можно встроить в CI: «упал валидатор — не запускаем тесты».
9. **Замер времени** — время проверки печатается в конце сводки с помощью
   **декоратора** (см. п. 5).
10. **Обработка ошибок** — нет файла, битый CSV/JSON, JSON — не список
    объектов, неизвестный формат файла, ошибка в конфиге, неизвестный тип
    отчёта — понятное сообщение и код выхода `2`, а не traceback.

## 4. Требования к правилам и данным

### 4.1. Правила (минимум 7)

| Правило | Параметры | Нарушение, если... |
|---|---|---|
| `required` | — | значение пустое или поля нет |
| `type` | `type`: `int`, `float`, `bool` или `str` | значение нельзя интерпретировать как этот тип (в CSV всё — строки, `"42"` — корректный `int`) |
| `range` | `min`, `max` (можно только один) | число вне диапазона |
| `length` | `min`, `max` (можно только один) | длина строки вне диапазона |
| `email` | — | не похоже на email: ровно одна `@`, непустая часть до неё, в домене есть точка, не в начале и не в конце, без пробелов. Без модуля `re` — строковыми методами |
| `one_of` | `values`: список | значения нет в списке |
| `unique` | — | значение уже встречалось в этом поле в предыдущих записях (правило помнит, что видело — сообщение указывает, где был первый раз) |

Можно добавлять свои правила (`not_in`, `starts_with`, `date` и т.п.) —
это плюс (п. 12).

### 4.2. Наборы данных (минимум 2)

- Не менее **2 своих наборов данных** разной природы (например,
  `users.csv` и `orders.json`) — и для каждого свой `rules/*.json`.
- В каждом наборе не менее **20 записей**, из них хотя бы 5 —
  с намеренно заложенными ошибками, задействующими **все** правила из
  4.1 хотя бы по разу (на двух наборах в сумме).
- Хотя бы один набор — CSV, хотя бы один — JSON.
- В README для каждого набора указано, **сколько нарушений ожидается и
  какие** — это одновременно документация и основа интеграционного теста
  (п. 8).

## 5. Требования к коду

### 5.1. ООП — обязательны все 4 принципа

Требование к ООП — центральная часть оценки. Ниже описано, **где именно**
каждый принцип должен быть виден в коде:

- **Абстракция.** `Rule` — абстрактный класс через `abc.ABC` с абстрактным
  методом `check(value, record_no)`, возвращающим нарушение или `None`.
  Так же абстрактными должны быть `DataLoader` (метод `load(path)`) и
  `Reporter` (метод `render(result)` или `write(result, path)`).
  Создать экземпляр самого `Rule`, `DataLoader` или `Reporter` нельзя.
- **Инкапсуляция.** Параметры правила проверяются при создании: у `range`
  и `length` `min` не больше `max` и хотя бы один из них задан, у
  `one_of` список не пустой, у `type` — только известные типы. Параметры
  хранятся в защищённых атрибутах и доступны только на чтение через
  `@property`. Состояние `unique` (что уже видели) спрятано внутри
  правила.
- **Наследование.** Каждое правило — наследник `Rule`; `CsvLoader` и
  `JsonLoader` — наследники `DataLoader`; четыре репортера — наследники
  `Reporter`. Общая логика (например, формирование нарушения или
  сохранение файла) — в родителе, наследники её используют через
  `super()` или вызов родительского метода.
- **Полиморфизм.** `Validator` прогоняет данные, вызывая
  `rule.check(...)` одинаково для любого правила — **без** `if
  rule.name == "range"` или `isinstance` в основном цикле. Так же
  выбирается загрузчик по расширению и репортер по аргументу `--report` —
  через словарь «имя → класс», а не цепочку `if/elif` с разным кодом в
  каждой ветке.

### 5.2. Остальные обязательные элементы

- **Фабрика правил.** Реестр `{"required": RequiredRule, "range":
  RangeRule, ...}` и функция/класс, превращающий конфиг в объекты правил —
  как стенд из JSON-конфига на практикуме по ООП (занятие 27-28).
- **dataclasses — минимум 1.** `Violation(record_no, field, rule, value,
  message)` — `@dataclass(frozen=True, order=True)`: нарушения неизменяемые
  и сортируются по номеру записи. Сводка — тоже удобно делать
  dataclass'ом.
- **Дандер-методы — минимум 2 осмысленных.** Например, `__str__` у
  `Violation` (строка для консоли), `__len__`/`__iter__`/`__bool__` у
  результата проверки (`if result:` — есть ли нарушения), `__repr__` у
  правил (`RangeRule(min=18, max=120)` — удобно в отладке и тестах).
- **Собственные исключения** с общим родителем: `ValidatorError` →
  `DataFileError` (нет файла, битый файл, неизвестный формат),
  `ConfigError` (ошибка в правилах), `ReportError` (названия — на
  усмотрение студента). `main.py` ловит `ValidatorError` в одном месте,
  печатает сообщение и выходит с кодом `2`.
- **Декоратор — минимум 1, по делу.** Например, `@timed`, замеряющий
  время проверки, или `@log_run`, дописывающий в `reports/runs.log` строку
  о каждом запуске (файл, правила, итог).
- **Модули и пакет.** Код разложен по модулям внутри пакета с
  `__init__.py`; `main.py` использует `if __name__ == "__main__":`.

## 6. Входные данные и конфиги

### 6.1. Данные — `data/users.csv` (пример)

```
id,name,email,age,role
1,Анна,anna@example.com,25,tester
2,Борис,boris@example,31,admin
3,,vika@example.com,17,tester
2,Олег,oleg@example.com,40,manager
5,Ия,iya@example.com,abc,guest
6,Пётр,anna@example.com,29,tester
```

JSON-набор — список объектов, например `data/orders.json`:

```json
[
  {"order_id": "A-100", "user_id": 1, "amount": 1590.0, "status": "paid", "promo": null},
  {"order_id": "A-101", "user_id": 2, "amount": -10, "status": "paid", "promo": "SALE10"},
  {"order_id": "A-101", "user_id": null, "amount": 300, "status": "lost", "promo": ""}
]
```

Номер записи — порядковый номер в файле, начиная с 1 (строка заголовка
CSV не считается).

### 6.2. Правила — `rules/users.json`

```json
{
  "dataset": "users",
  "fields": {
    "id":    [{"rule": "required"}, {"rule": "type", "type": "int"}, {"rule": "unique"}],
    "name":  [{"rule": "required"}, {"rule": "length", "min": 2, "max": 50}],
    "email": [{"rule": "required"}, {"rule": "email"}, {"rule": "unique"}],
    "age":   [{"rule": "type", "type": "int"}, {"rule": "range", "min": 18, "max": 120}],
    "role":  [{"rule": "one_of", "values": ["guest", "tester", "admin"]}]
  }
}
```

`dataset` используется в имени файла отчёта: `reports/users_report.md`.

### 6.3. Отчёт — `reports/users_report.json` (пример структуры)

```json
{
  "source": "data/users.csv",
  "rules": "rules/users.json",
  "summary": {
    "records": 6,
    "valid": 1,
    "invalid": 5,
    "violations": 7,
    "by_rule": {"unique": 2, "email": 1, "required": 1, "range": 1, "one_of": 1, "type": 1},
    "by_field": {"email": 2, "age": 2, "name": 1, "id": 1, "role": 1}
  },
  "violations": [
    {"record_no": 2, "field": "email", "rule": "email", "value": "boris@example", "message": "некорректный email"}
  ]
}
```

(в примере показано одно нарушение из семи — в настоящем отчёте все.)

Требования к работе с файлами:

- Чтение — через `with open(..., encoding="utf-8")`, модули `csv`
  (`DictReader`/`DictWriter`) и `json`; запись JSON с
  `ensure_ascii=False` и `indent`.
- Вся работа с файлами — в загрузчиках, загрузчике конфига и репортерах;
  в правилах и в `Validator` нет ни одного `open()`.
- Пути передаются параметрами (а не зашиты внутри методов) — иначе их не
  получится протестировать на временных файлах.

## 8. Автотесты (pytest) — обязательная часть

- Тесты лежат в `tests/`, общие фикстуры — в `tests/conftest.py`, в корне
  проекта — `pytest.ini` с `pythonpath = .` (как на занятии 29-30).
  Команда `pytest` из папки проекта запускает все тесты без ошибок
  импорта.
- **Не меньше 20 тестов**, все зелёные на момент сдачи.
- **Не меньше 3 фикстур**, например: небольшой список записей-словарей,
  словарь конфига правил, CSV-файл и JSON-файл во временной папке.
- **Хотя бы одна фикстура использует `tmp_path`** (или `yield` с уборкой):
  тесты загрузчиков и репортеров работают с временными файлами, а не с
  `data/` и `reports/` проекта.
- **`pytest.raises`** — на каждое собственное исключение хотя бы один тест
  (битый JSON, неизвестное правило, `min > max`, неизвестный формат и т.д.).
- **Хотя бы один тест-класс** — например, `class TestRangeRule:`.
- Что обязательно покрыть:
  - **каждое правило** — минимум два теста: «корректное значение проходит»
    и «некорректное ловится»; у `range`/`length` — граничные значения
    (ровно `min`, ровно `max`);
  - `unique` — первое вхождение проходит, повторное ловится, и в
    сообщении номер первой записи;
  - пустые значения пропускаются всеми правилами, кроме `required`;
  - `CsvLoader` и `JsonLoader` на временных файлах, включая битый файл;
  - фабрика правил: корректный конфиг → нужные классы с нужными
    параметрами; некорректный → `ConfigError`;
  - хотя бы один репортер пишет файл, и его содержимое правильное
    (например, CSV-отчёт читается обратно `csv.DictReader` и в нём
    ожидаемое число строк);
  - **интеграционный тест**: на вашем наборе данных из `data/` валидатор
    находит ровно столько нарушений, сколько заявлено в README.
- Имена тестов говорят, что проверяется:
  `test_range_rule_accepts_exact_max`, а не `test_3`.

`@pytest.mark.parametrize`, маркеры и HTML-отчёты не требуются (это темы
следующих занятий) — но если разберётесь сами, это плюс (п. 12).

- Никаких traceback при некорректных аргументах, файлах и конфигах.
- Читаемые сообщения (на русском или английском — на выбор, но

- Дополнительные правила: `date` (формат `ГГГГ-ММ-ДД`), `not_in`,
  `starts_with`, правило, сравнивающее два поля записи (например,
  `end_date` не раньше `start_date`).
- Флаг `--fail-fast`: остановиться на первой записи с ошибкой.
- Флаг `--only email,age`: проверить только часть полей.
- Проверка «лишних» полей: в записи есть поле, которого нет в конфиге.
- Генератор «чистых» тестовых данных по тому же конфигу (вспомните
  практикум 19-20).
- Цветной вывод в терминале.

## 13. Порядок сдачи работы (через GitHub)

Репозиторий курса: https://github.com/ZakharMarinin/QA621-Final-Project

1. Сделать **fork** репозитория к себе на GitHub.
2. Склонировать свой форк локально: `git clone <ссылка-на-форк>`.
3. Разрабатывать проект в отдельной ветке (например,
   `feature/<github-логин>` или `submit/<фамилия>`) либо в `main` своего
   форка.
4. Весь проект — в папке `students/<фамилия_имя>/` (латиницей, например
   `students/ivanov_ivan/`). Файлы вне своей папки не менять.
5. Коммитить регулярно, с понятными сообщениями — история коммитов
   учитывается при проверке как отражение процесса работы, а не только
   финальный результат. Один коммит «всё готово» в последний вечер —
   минус.
6. Не коммитить `venv/`, `__pycache__/`, `.pytest_cache/` (они уже есть в
   `.gitignore` репозитория).
7. Приложить README с инструкцией запуска и кратким описанием проекта.
8. Перед открытием PR запустить `pytest` из папки проекта — все тесты
   должны проходить.
9. По готовности открыть **Pull Request** из своего форка в исходный
   (upstream) репозиторий: https://github.com/ZakharMarinin/QA621-Final-Project.
10. Название PR: `Фамилия Имя — Валидатор` (пример:
    `Иванов Иван — Валидатор`).
11. В описании PR указать, что реализовано, сколько тестов и какие есть
    известные ограничения или недоделанные пункты.
12. **Дедлайн: PR открыт не позже 21 октября 2026 года, 23:59.**
    Изменения после дедлайна не учитываются, если не указано иное.
13. Проверка и обсуждение идут в комментариях к PR; доработки вносятся
    новыми коммитами в ту же ветку — они появляются в PR автоматически,
    без создания нового PR.
14. **Защита — 22 октября 2026 года** на занятии: около 10 минут на
