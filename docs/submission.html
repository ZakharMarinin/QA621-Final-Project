Как сдавать работу

Порядок один и тот же для обоих заданий — отличается только заголовок pull request. Работа сдаётся через GitHub: fork, ветка, коммиты, PR в репозиторий курса, а затем защищается на экзамене.

Дедлайн: 21 октября 2026 года, 23:59. Pull request должен быть открыт до этого момента — изменения после дедлайна не учитываются, если не указано иное. Защита — 22 октября 2026 года.

Сделайте fork репозитория

Форкните QA621-Final-Project к себе на GitHub.

Склонируйте форк локально

git clone <ссылка-на-форк>

Работайте в отдельной ветке

Например, feature/<github-логин> или submit/<фамилия> — либо прямо в main своего форка.

Только в своей папке

Весь проект — в students/<фамилия_имя>/ латиницей, например students/ivanov_ivan/. Файлы вне своей папки не меняйте.

Коммитьте регулярно

С понятными сообщениями — история коммитов учитывается как отражение процесса работы, а не только финальный результат. Один коммит «всё готово» в последний вечер — минус.

Не коммитьте мусор

venv/, __pycache__/, .pytest_cache/ уже в .gitignore репозитория — проверьте git status перед коммитом.

Приложите README

Инструкция запуска, список команд, как запустить тесты и краткое описание проекта — обязательны.

Прогоните тесты

Из папки проекта: pytest -v. Все тесты должны проходить — красные тесты в PR означают, что работа не готова.

Откройте Pull Request

Из своего форка в исходный (upstream) репозиторий, когда проект готов к проверке.

Назовите PR правильно

Фамилия Имя — Название проекта, например Иванов Иван — Магазин.

Опишите, что реализовано

В описании PR — что сделано, сколько тестов и какие есть известные ограничения или недоделанные пункты.

Успейте до дедлайна

Работа считается сданной с момента открытия PR — не позже 21 октября 2026 года, 23:59; изменения после дедлайна не учитываются, если не указано иное.

Дорабатывайте в том же PR

Проверка и обсуждение идут в комментариях к PR; доработки — новыми коммитами в ту же ветку, без создания нового PR.

Заголовок PR зависит от проекта:
  • Магазин — Фамилия Имя — Магазин
  • Валидатор — Фамилия Имя — Валидатор

Защита 22 октября

Около 10 минут на человека, проект запускается с вашего ноутбука из склонированного репозитория.

  1. Демонстрация — основные сценарии в терминале, включая ошибочный ввод: неизвестный товар, битый файл, неверный конфиг.
  2. Тесты — живой прогон pytest -v; рассказать, какие фикстуры есть и зачем.
  3. Архитектура — какие классы, кто от кого наследуется, где каждый из 4 принципов ООП и почему так.
  4. Вопросы — по любому месту кода. Умение объяснить свой код весит столько же, сколько сам код.
