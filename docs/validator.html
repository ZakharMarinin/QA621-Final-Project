Валидатор

Консольный QA-инструмент: проверяет файл с тестовыми данными (CSV или JSON) по правилам из отдельного JSON-конфига и сохраняет отчёт о нарушениях. Плюс набор тестов на pytest — на сам валидатор.

Суть проекта

Прежде чем заливать тестовые данные на стенд или гонять на них автотесты, их проверяют — иначе тест падает не из-за бага в продукте, а из-за кривого age = "abc" в фикстуре. Валидатор делает именно это: обязательные поля, типы, диапазоны, длина, email, допустимые значения, уникальность.

Ключевая идея: правила — это данные, а не код. Чтобы проверить новый файл, пишут новый rules.json, а не правят Python. Вторая половина задания — автотесты на pytest; без них проект не принимается.

пример вызовов
$ python main.py check data/users.csv --rules rules/users.json
$ python main.py check data/users.csv --rules rules/users.json --report md
$ python main.py check data/orders.json --rules rules/orders.json --report csv
$ python main.py rules
пример вывода
$ python main.py check data/users.csv --rules rules/users.json --report md

Точный формат вывода — на ваше усмотрение; номер записи, поле, правило, сообщение и сводка — обязательны. Интерактивное меню здесь не подходит: такие утилиты запускают из скриптов и CI.

Что нужно реализовать

  1. Загрузка данных — CSV с заголовком или JSON-список объектов, формат по расширению. Дальше валидатор работает одинаково с любым форматом.
  2. Загрузка правил — JSON-конфиг превращается в объекты правил и проверяется до прогона: неизвестное правило, нет параметра, min > max — ошибка с указанием поля и правила.
  3. Прогон — каждая запись проверяется правилами своих полей; нарушение — объект с номером записи, полем, правилом, значением и сообщением.
  4. Пустые значения — проверяет только required, остальные правила их пропускают. Иначе одно пустое поле даст пять одинаковых ошибок.
  5. Сводка — всего записей, без ошибок, с ошибками, нарушений; количество по каждому правилу и по каждому полю.
  6. Отчёты — console (по умолчанию), csv, json, md. Файлы — в reports/, папка создаётся сама.
  7. Список правил — команда rules печатает правила и параметры из того же реестра, что использует фабрика.
  8. Код выхода — 0 нарушений нет, 1 есть нарушения, 2 ошибка запуска (файл, конфиг, аргументы). Так утилиту можно встроить в CI.
  9. Замер времени — время проверки в сводке, через декоратор.
  10. Обработка ошибок — нет файла, битый CSV/JSON, JSON не список, неизвестный формат, ошибка в конфиге, неизвестный тип отчёта — понятное сообщение и код 2, а не traceback.

Требования к ООП

Все четыре принципа обязательны и должны присутствовать по существу, а не для галочки.

Абстракция

Rule — абстрактный класс через abc.ABC с check(value, record_no), возвращающим нарушение или None. Так же абстрактные DataLoader (load(path)) и Reporter.

Инкапсуляция

Параметры правила проверяются при создании (min ≤ max, непустой values, известный type) и доступны только на чтение через @property. Память unique спрятана внутри правила.

Наследование

Каждое правило — наследник Rule; CsvLoader/JsonLoader — наследники DataLoader; четыре репортера — наследники Reporter. Общая логика — в родителе.

Полиморфизм

Validator вызывает rule.check(...) одинаково для любого правила — без if rule.name == "range" и isinstance. Загрузчик и репортер выбираются через словарь «имя → класс».

Также обязательно

  • Фабрика правил — реестр {"required": RequiredRule, "range": RangeRule, ...} превращает конфиг в объекты, как стенд на практикуме 27-28.
  • dataclass — Violation(record_no, field, rule, value, message) с frozen=True, order=True: неизменяемое и сортируется по номеру записи.
  • Дандеры — минимум 2 по делу: __str__ у нарушения, __len__/__iter__/__bool__ у результата, __repr__ у правил.
  • Свои исключения с общим родителем ValidatorError: DataFileError, ConfigError, ReportError. main.py ловит их в одном месте и выходит с кодом 2.
  • Декоратор — @timed для замера проверки или @log_run, пишущий строку о каждом запуске в reports/runs.log.
  • Пакет — модули внутри пакета с __init__.py, в main.py — if __name__ == "__main__":.

Автотесты на pytest

Обязательная часть проекта и отдельный критерий оценки. На защите — живой прогон pytest -v.

20+
тестов, все зелёные
3+
фикстуры в conftest.py
1+
фикстура с tmp_path или yield
1+
тест-класс
  • Структура: tests/, tests/conftest.py, в корне pytest.ini с pythonpath = . — как на занятии 29-30.
  • Каждое правило — минимум «корректное проходит» и «некорректное ловится»; у range/length — граничные значения.
  • unique — повтор ловится, в сообщении номер первой записи. Пустые значения пропускаются всеми правилами, кроме required.
  • Загрузчики — на временных файлах, включая битый файл. Фабрика — корректный конфиг даёт нужные классы, некорректный — ConfigError.
  • Хотя бы один репортер пишет файл с правильным содержимым (например, CSV читается обратно csv.DictReader).
  • Интеграционный тест: на вашем наборе из data/ ровно столько нарушений, сколько заявлено в README.
  • pytest.raises — на каждое собственное исключение. Имена тестов говорят, что проверяется: test_range_rule_accepts_exact_max.
  • parametrize, маркеры и HTML-отчёты не требуются — но приветствуются.

Нефункциональные требования

  • Python 3.10+, только стандартная библиотека (+ pytest для тестов).
  • Никаких traceback при некорректных аргументах, файлах и конфигах.
  • Сообщения на русском или английском, но единообразно.
  • README: запуск, все правила и их параметры, формат конфига, свои наборы данных с ожидаемым числом нарушений, коды выхода, как запустить тесты.

Идеи для дополнительных баллов

  • @pytest.mark.parametrize для тестов правил.
  • Свои правила: date, not_in, starts_with, сравнение двух полей записи.
  • Флаги --fail-fast и --only email,age.
  • Поиск «лишних» полей, которых нет в конфиге.
  • Генератор «чистых» тестовых данных по тому же конфигу — привет практикуму 19-20.
  • Цветной вывод в терминале.
