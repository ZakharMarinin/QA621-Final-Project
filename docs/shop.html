Задание 1

Магазин

Консольное приложение небольшого интернет-магазина: каталог, корзина, промокоды, оформление и отмена заказов, учёт остатков. Данные живут в JSON-файлах между запусками, а набор тестов на pytest доказывает, что всё считается правильно.

Суть проекта

Товары разных типов по-разному считают стоимость и ограничивают количество, промокоды разных типов по-разному считают скидку. «Оформить заказ» — значит списать товары со склада и записать заказ в JSON; это не веб-сервер и не настоящая оплата.

Вторая половина задания — автотесты на pytest. Магазин — система, которую вы не только пишете, но и тестируете. Без тестов проект не принимается.

Формат запуска — аргументы командной строки (sys.argv или argparse) либо интерактивное меню; выбор описывается в README.

пример вызовов
$ python main.py catalog --category coffee
$ python main.py search кофе
$ python main.py show P003
$ python main.py cart add P003 2
$ python main.py cart add P010 0.35
$ python main.py cart set P003 1
$ python main.py cart remove P003
$ python main.py cart show
$ python main.py promo SALE10

$ python main.py export-orders reports/orders.csv

Названия команд можно адаптировать — набор сценариев ниже должен быть покрыт полностью.

Что нужно реализовать

  1. Каталог — артикул, название, категория, цена, остаток; фильтр по категории.
  2. Поиск — по подстроке в названии, без учёта регистра.
  3. Карточка товара — подробности, включая тип и его особенности («цена за кг», «цифровой»).
  4. Корзина — добавить, изменить количество, убрать, показать: строки, суммы по строкам, сумма без скидки, скидка, итог. Повторное добавление увеличивает количество, а не создаёт вторую строку.
  5. Промокод — один на корзину, новый заменяет старый. Неизвестный код или невыполненное условие — понятное сообщение.
  6. Оформление заказа — проверка остатков по всем позициям, списание, заказ со статусом new, очистка корзины. Не хватает хотя бы одной позиции — заказ не создаётся и склад не меняется вообще.
  7. История заказов — список заказов и просмотр конкретного.
  8. Отмена заказа — статус cancelled, остатки возвращаются на склад; повторная отмена — ошибка.
  9. Приход товара — увеличение остатка.
  10. Экспорт — все заказы в CSV: номер, статус, позиций, сумма, скидка, итог.
  11. Журнал действий — значимые действия пишутся в data/shop.log с помощью декоратора.
  12. Обработка ошибок — неизвестный артикул, количество ≤ 0 или не число, нехватка остатка, неверный промокод, пустая корзина, отсутствующий или битый JSON — понятное сообщение, а не traceback.

Требования к ООП

Все четыре принципа обязательны и должны присутствовать по существу, а не для галочки.

Абстракция

Product — абстрактный класс через abc.ABC с методами вроде line_price(qty) и check_qty(qty). Discount — абстрактный с apply(cart). Создать их напрямую нельзя.

Инкапсуляция

Цена и остаток — защищённые _price, _stock за @property. Сеттеры валидируют: цена > 0, остаток ≥ 0. Списать больше, чем есть, нельзя — собственное исключение.

Наследование

PieceProduct, WeightProduct, DigitalProduct — наследники Product с super().__init__(); типы промокодов — наследники Discount.

Полиморфизм

Корзина зовёт product.line_price(qty) и discount.apply(cart), не проверяя тип через isinstance или if type == "weight".

Также обязательно

  • Композиция — Cart хранит строки и промокод, сервис владеет каталогом, корзиной и заказами.
  • Дандеры — минимум 2 по делу: __len__, __iter__, __contains__, __bool__ у корзины, __str__ у заказа.
  • dataclass — минимум 1: CartItem, Order; asdict() для сохранения.
  • Свои исключения с общим родителем ShopError: ProductNotFoundError, OutOfStockError, InvalidPromoError, EmptyCartError и т.п. CLI ловит ShopError в одном месте.
  • Декоратор — например, @log_action, пишущий действия сервиса в data/shop.log.
  • Фабрика из JSON — промокоды из конфига превращаются в объекты через словарь {"percent": PercentDiscount, ...}, как стенд на практикуме 27-28.

Хранение данных

Три JSON-файла в data/, вся работа с ними — через класс Repository, которому путь передаётся параметром (иначе его не протестировать на временных файлах). Сохранение — после каждого изменяющего действия. Нет orders.json — создаётся пустой; нет или битый каталог/промокоды — понятное сообщение.

Автотесты на pytest

Обязательная часть проекта и отдельный критерий оценки. На защите — живой прогон pytest -v.

1+
тест-класс
  • Структура: tests/, tests/conftest.py, в корне pytest.ini с pythonpath = . — как на занятии 29-30.
  • Тесты не трогают настоящие data/*.json — только временные файлы.
  • pytest.raises — на каждое собственное исключение.
  • Покрыть: стоимость строки для каждого типа товара (включая округление у весового); ограничения количества для каждого типа; каждый промокод, включая «порог не выполнен»; оформление уменьшает остатки, а при нехватке не меняет склад вообще; отмена возвращает остатки; Repository — сохранили, загрузили, совпало, а битый JSON даёт своё исключение.
  • Имена говорят, что проверяется: test_weight_product_rounds_line_price_to_kopecks, а не test_1.
  • parametrize, маркеры и HTML-отчёты не требуются — но приветствуются.

Идеи для дополнительных баллов

  • @pytest.mark.parametrize для тестов промокодов и типов товаров.
  • Несколько промокодов одновременно с правилами совместимости.
  • Отчёт по продажам: выручка по категориям, самый продаваемый товар, средний чек.
  • Статусы заказа new → paid → shipped с проверкой допустимых переходов.
  • Атомарная запись JSON — во временный файл и переименование.
  • Цветной вывод в терминале.
